Search Intelligence Research: Content Performance Analysis and Prioritization

Abstract

This research investigates whether observed search and content-performance signals can help prioritize content pages for review. The analysis uses an anonymized dataset from the FlyRank ML Internship repository containing content-level search and engagement signals. A Logistic Regression model was evaluated against a transparent Week-4 baseline using the same fixed held-out test split. On this split, the Logistic Regression model achieved 0.8812 accuracy and 0.8618 F1, compared with 0.3397 accuracy and 0.4736 F1 for the baseline. These measured results support using the model as decision-support for content prioritization, while human review remains necessary before taking action.

Introduction / Problem Statement

Content teams may need to review many pages but cannot investigate every page with the same level of attention. The FlyRank content problem used as the case study for this research is therefore content prioritization: identifying which pages may deserve review based on observed search and engagement signals.

This research does not claim that changing a page will guarantee improved future performance. Instead, it investigates whether patterns in the supplied anonymized data can provide useful decision-support for deciding which content should be reviewed, monitored, or investigated first.

Research Question

Can a simple machine-learning model identify higher-performing and lower-performing content patterns more effectively than the Week-4 baseline rule?

Data

The analysis uses the anonymized CSV dataset provided in the FlyRank ML Internship repository. The file contains content-level search and engagement signals including search volume, impressions, clicks, sessions, CTR, average position, engagement measures, content age, freshness information, and AI traffic.

The Hugging Face warehouse dataset was not used because it could not be reliably accessed. The repository CSV was therefore used consistently for the remaining analysis. No client names, URLs, or private search queries were used. Fields that could directly reveal the prediction target were excluded from the model features.

Methodology

The project uses supervised classification. A performance label was created from observed clicks in the supplied dataset: pages with clicks above the dataset median were treated as the higher-performance class, while pages at or below the median were treated as the lower-performance class.

A Logistic Regression model was selected because it is relatively simple and interpretable. Numeric search and content signals were used as model features, and missing numeric values were filled using the median. The data was divided into a fixed 80% training set and 20% test set, with the same held-out observations used to compare the model and baseline.

Feature and leakage checks were performed during the analysis. The target column and directly excluded fields were not intentionally included as model features.

Results

The Logistic Regression model and Week-4 baseline were evaluated on the same held-out test set of 6,000 observations.

Method Accuracy Precision Recall F1 Score
Week-4 Baseline 0.3397 0.3614 0.6867 0.4736
Logistic Regression 0.8812 0.8670 0.8566 0.8618

On this measured split, Logistic Regression performed better than the transparent baseline across the reported metrics. This result is descriptive and directional: it shows better measured performance on this particular held-out split and does not establish that the model will always outperform the baseline on future data.

Limitations and Honest Framing

The analysis uses the repository CSV rather than the full production warehouse, so the findings should not be treated as representative of all production data. The performance label is derived from observed clicks in the supplied dataset and is therefore an observed proxy rather than a direct measure of future performance.

Search signals such as CTR, position, impressions, and clicks may be related to one another. The model therefore identifies measured patterns and associations rather than proving independent causal effects.

The model and recommendations are intended for decision-support only. They should not automatically publish, remove, rewrite, or otherwise change content.

Ranked Recommendations

The final action playbook creates a ranked content-review queue using observed signals. Pages with higher search volume, lower CTR, and older update status can receive higher review priority.

The main reason codes include:

  • HIGH_VOLUME_LOW_CTR: Review CTR opportunity.
  • STALE_CONTENT: Review for refresh.
  • MONITOR: Continue monitoring.

A high rank does not mean that a page is definitely performing poorly or that refreshing it will definitely improve performance. Human reviewers should consider actual content, search intent, business context, and recent changes before taking action.

Reproducibility

The analysis is supported by executed notebooks covering feature and leakage checks, signal audit, baseline scoring, machine-learning modeling, validation audit, action playbook development, and the final capstone.

The model-versus-baseline results and ranked recommendations can be regenerated from the anonymized repository dataset and project notebooks.
